# Chat Versus Repository Reconciliation

## Scope and Method

This document compares historical project evidence in `docs/history/` with the static repository evidence in `docs/audit/`. It does not treat either layer as approved business policy, does not treat conversational completion claims as implementation proof, and does not treat source verification as runtime verification.

The current repository head and the original audited application commit are both `7343e9e1194ffe32e2aa607be509ff0149d86675`. No additional application-source check was required for this comparison; application paths below are traceability references already established by the audit.

The reconciliation classification applies to the relationship between the two evidence layers. Audit labels such as `SOURCE_VERIFIED`, `INFERRED_FROM_CODE`, and `NEEDS_RUNTIME_VERIFICATION` retain their meanings from `docs/audit/AUDIT-METADATA.md`.

## High-Impact Reconciliation Notes

### Authentication policy is not settled by the login screen

The username-labelled UI, dual-identifier backend, public registration endpoints, database-default Armada role, nullable operational emails, and email-oriented recovery paths describe different account contracts. No single layer supplies stakeholder approval for their combination. AU-02 through AU-05 must therefore remain separate decisions rather than being summarized as “Breeze authentication is complete.”

### Stock is operationally aggregate-based but not fully explainable by its ledger

The current balance is read from `raw_materials.sealed_stock` and `opened_stock`. Transaction rows snapshot restock and manual adjustments, while production consumption, package opening, and production waste are missing from that ledger. History strongly values explainable movement, but it also deferred a production-consumption ledger. The safe present statement is therefore: aggregate columns drive operations; the ledger is partial; the approved reconciliation/source-of-truth policy is unresolved.

### Production output and one-time completion are critical unresolved semantics

The source books full target output and leaves `actual_quantity` at zero. The same completion method lacks a visible state/idempotency guard. These are not cosmetic reporting differences: they can affect raw-material stock, finished-goods batches, waste, distribution availability, and every derived report. Historical questions about target versus actual do not authorize either behavior.

### Distribution records custody quantities, not auditable sales or revenue

Finished goods leave ready stock at allocation, while later Armada input overwrites cumulative sold quantities. That supports a dispatch/return workflow but not event-level sales, price, payment, customer, or revenue reporting. Historical commercial goals remain unimplemented, and current menu price must not be retroactively treated as a sale-price snapshot.

### ROP/MRP terminology must remain narrow

History deliberately phased ROP and simplified MRP. The repository currently supplies static stock alerts and advisory current-BOM reservations. Calling those features full ROP or MRP would contradict both evidence layers. Forecasting, safety stock, lead time, procurement recommendations, and lot sizing remain roadmap/decision topics.
