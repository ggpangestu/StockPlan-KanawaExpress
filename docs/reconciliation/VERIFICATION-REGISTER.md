# Verification Register

## Purpose and evidence boundary

This register reconciles the static repository audit in `docs/audit/` with the historical conversation extracts in `docs/history/`. It does not adopt historical discussion as current policy, does not treat source inspection as runtime proof, and records no stakeholder answer.

Every entry is pending. A later reviewer must preserve the original evidence, attach new evidence, and record a separate decision or observed result. No check in this register was executed while creating this document.

## Priority rules

| Priority | Meaning |
|---|---|
| `P0` | Security, data-integrity, duplicate-effect, irreversible-history, or accounting-boundary questions that can invalidate core records. |
| `P1` | Core workflow and business-rule questions needed to describe normal inventory, production, distribution, and return operations. |
| `P2` | Reporting, UI, maintainability, deployment, operations, and documentation-validity checks. |
| `P3` | Future scope, portability, forecasting, advanced planning, and cleanup questions that do not define the current core transaction path. |

## Reconciliation classifications

Only the following classifications are used in this register:

- `ALIGNED`
- `PARTIALLY_ALIGNED`
- `IMPLEMENTED_BUT_UNDOCUMENTED`
- `INTENDED_NOT_IMPLEMENTED`
- `HISTORICAL_PLAN_ONLY`
- `SUPERSEDED_HISTORY`
- `IMPLEMENTATION_CONFLICT`
- `BUSINESS_DECISION_REQUIRED`
- `RUNTIME_VERIFICATION_REQUIRED`
- `UNKNOWN`

## Verification types

The verification type identifies the principal next evidence source. It does not authorize executing that verification.

- `HUMAN_CONFIRMATION`
- `COLLABORATOR_CONFIRMATION`
- `SOURCE_RECHECK`
- `RUNTIME_TEST`
- `DATABASE_INSPECTION`
- `BUSINESS_PROCESS_VALIDATION`
